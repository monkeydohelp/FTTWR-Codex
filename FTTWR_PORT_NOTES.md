## Required XML schema gate

Before deploying any ported XML, run DevKit\Validate-Civ4Xdr.ps1 against every changed game XML file and its matching XDR schema. The validator also rejects XDR maxOccurs values that Civ4's MSXML 3 parser cannot load and yield arrays exceeding the DLL's three-yield limit. Follow FTTWR_XML_PORT_VALIDATION.md. Do not treat XML well-formedness or a Civ4 Load XML ... SUCCEEDED log line as schema validation; verify root collection membership and child element order, then run cross-file reference checks.

## 2026-09-25 — ACBase/Fallout XML omission-default contract and improvement reader assert

- Engineering rule for all future ports: Fallout and ACBase/AdvCiv have materially different XML omission/default contracts. Never infer that a tag can be omitted in the receiving mod because it is omitted in the source mod, or infer a DLL runtime default from XDR `minOccurs="0"`. XDR permits/forbids document structure; it does not assign C++ defaults. Before porting a record, check source schema/reader/effective values and receiving schema/order, `Cv...Info::read` and `readPass2` fallback overloads, and receiving constructor defaults. Preserve source semantics explicitly where they differ, unless a separate design decision approves changing behavior.
- The launch assert named missing `iAdvancedStartCost` in `CIV4ImprovementInfos.xml`. The four imported lairs were sparse Fallout records whose source reader/schema tolerated omitted fields; the receiving `CvImprovementInfo::read` has direct no-fallback reads even though the ACBase XDR marks these fields optional. `readPass2` also directly requires `ImprovementPillage` and `ImprovementUpgrade`.
- Added missing direct-reader fields to `IMPROVEMENT_RAD_BEAR_DEN`, `IMPROVEMENT_DEATHCLAW_DEN`, `IMPROVEMENT_RAD_SCORPION_DEN`, and `IMPROVEMENT_RAD_SPIDER_DEN` in receiving XDR order. Fallout's source schema comments specify `iAdvancedStartCost=-1` and `iAirBombDefense=-1`; the former preserves the DLL behavior that lairs cannot be bought in Advanced Start. Remaining omitted numeric and boolean fields use the verified receiving constructor zero/false defaults. Both improvement-reference tags use the accepted receiving `NONE` sentinel. Existing spawn data, lair appearance rates, pillage arrays, and bonus-validity data are preserved.
- Validation/evidence: record-completeness inspection covers all 26 no-fallback scalar/boolean/reference fields checked across `CvImprovementInfo::read` and `readPass2`.
