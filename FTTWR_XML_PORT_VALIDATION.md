# Required Civ4 XML Port Validation

Run the XDR structural validator on every changed game XML file before copying it into either FTTW-R Test deployment. A normal XML parse is not a schema check: Civ4 can log a file as loaded while a record is outside its declared collection, then fail to register that record's Type.

From the mod root, run the validator once per changed XML file, pairing it with the schema named by that file's x-schema namespace. Example:

    powershell -NoProfile -ExecutionPolicy Bypass -File .\DevKit\Validate-Civ4Xdr.ps1 -XmlPath .\Assets\XML\Technologies\CIV4TechInfos.xml -SchemaPath .\Assets\XML\Technologies\CIV4TechnologiesSchema.xml

The check validates well-formedness, the root type and collection nesting, required/optional/repeated elements, element order, and XDR integer/boolean lexical values. It rejects a UTF-8 BOM because the Civ4 loader in this project has reported it as invalid at document start. Unsupported XDR constructs fail closed rather than returning a false pass.

The target game's XML loader uses the legacy MSXML 3 XDR parser: for `maxOccurs`, it accepts only `1` or `*`. A numeric bound greater than one can pass a modern parser or a structural-only validator but prevent Civ4 from loading the schema. `Validate-Civ4Xdr.ps1` therefore rejects any other `maxOccurs` value and checks that repeated `iYield`/`iYieldChange` arrays do not exceed the DLL's `NUM_YIELD_TYPES=3`; keep the XDR occurrence as `*` and enforce the fixed array size as a separate data check. The validator is the required pre-deployment schema gate; where practical, also probe changed XML with `Msxml2.DOMDocument.3.0` (`validateOnParse` and `resolveExternals` enabled) to match the runtime parser.

Also run the existing cross-file Type/prerequisite/reference checks after the schema check. XDR validates one document's structure; it does not prove that referenced tech, unit, art, text, or other IDs are defined in their owning files. Finally, keep game startup testing separate: schema pass is static evidence, not runtime evidence.

For a unit/improvement/build port, verify every `BuildType` in both `CIV4UnitInfos.xml` and `CIV4ImprovementInfos.xml` exists in `CIV4BuildInfos.xml`. For each imported BuildInfo, also resolve its non-`NONE` prerequisite tech, improvement, route, entity event, and feature-struct references; for each new route, resolve its bonus and tech-movement references. Preserve existing receiver records when merging a Fallout collection, and check IDs for duplicates after the merge. A schema-valid owner file can still assert when its referenced Info ID is absent.

## Native DLL reader requirements (beyond XDR)

Fallout and ACBase/AdvCiv have materially different XML omission/default contracts. Do not assume a tag omitted safely by one mod can be omitted in the other, or that a target's schema optionality means its DLL reader can omit that tag. XDR `minOccurs="0"` only permits omission during validation; it does not inject a runtime value into a C++ member.

For every cross-mod record, inspect the receiving mod's XDR field names and sequence, the matching `Cv...Info::read` and `readPass2` calls (including whether an explicit fallback argument is supplied), and the receiving constructor's initialized values. Separately inspect the source mod's schema comments, reader behavior, and actual source-record values to establish the effective source default/semantics. If the receiving DLL requires a node that the source omits, add the verified equivalent explicitly at the receiving XDR-defined position; do not blindly copy the target constructor's value when that would change source behavior. Retain all explicit source values and record any deliberate semantic adaptation. Treat an omission/default-contract audit as a required part of porting, not as an optional follow-up. Run the completeness scan over the entire owning XML collection, not only records edited in the latest batch; a previously imported or existing record can be the next failing record.

Changing XDR optionality alone cannot solve reader-side omission asserts. Any broader change to make ACBase readers supply defaults must be an intentional DLL-wide compatibility refactor: audit each field's semantics, add explicit reader fallbacks where safe, and test all XML classes that share those readers. Do not infer that the two mods should share one default policy merely because their content overlaps.
## Required-field sentinels and C: handoff

Before removing a field, inspect the receiving XDR for minOccurs and compare a known-good record. A behavior can be disabled while a schema-required element remains; use the receiving schema's accepted sentinel (for example, this target requires ReligionInfo.TechPrereq, so disabled founding uses NONE rather than deleting the element).

For an installed C: test handoff, treat the E: candidate as the source of truth: validate each changed E: XML file first, update the E: port notes, copy the exact changed XML and notes to C:, validate the C: copies against C:'s own schemas, then compare E:/C: SHA-256 hashes. Keep schema, cross-reference, launch, and human in-game evidence distinct.

For terrain bonus records, include `CvBonusInfo::read`'s direct no-fallback fields in the record-completeness check. In this DLL they include `iAITradeModifier`, `iAIObjective`, `iHealth`, `iHappiness`, `iMinAreaSize`, `iMinLatitude`, `iPlacementOrder`, `iConstAppearance`, placement/group scalars, and area/terrain booleans; check `Rands` children when that wrapper is present. Confirm each omitted value from the receiving constructor before filling it, retain explicit source values, and place fields in `CIV4TerrainSchema.xml` order. The 2026-09-25 missing-`iAIObjective` launch assert showed that schema-valid optionality alone does not guarantee this loader can omit the field.

For improvement records, include `CvImprovementInfo::read`'s direct no-fallback scalars/booleans and `readPass2`'s `ImprovementPillage`/`ImprovementUpgrade` in the same completeness audit. For the four Fallout lairs imported on 2026-09-25, preserve the source schema's `-1` defaults for advanced-start purchase cost and air-bomb defense; use the verified target constructor zero/false defaults for the remaining omitted scalars/flags, and use the target `NONE` sentinel for both improvement references. Place these fields in the receiving `CIV4TerrainSchema.xml` order.

For feature and bonus records, resolve every `FeatureInfo.ArtDefineTag` against a `FeatureArtInfo.Type` in the active `CIV4ArtDefines_Feature.xml` and every `BonusInfo.ArtDefineTag` against a `BonusArtInfo.Type` in `CIV4ArtDefines_Bonus.xml`; XDR-valid XML can still assert later when the art manager requests a missing type. For bonus resources, inspect every used model's embedded NIF texture references as well as its NIF/KFM/SHADERNIF and button/atlas dependencies. A present model and valid XML art ID do not prove its material textures are installed; missing DDS files can render the model magenta. Copy Fallout-specific dependencies that are absent from the target, or verify stock BtS paths are supplied by the installed game assets. Keep source font-button mappings unless a separate icon/UI decision changes them.

For every `Description`, `Civilopedia`, and `Help` text key changed during a port, verify there is one matching `<Tag>` with non-empty English text in a loaded `Civ4GameText` file. Keep the expected `<Tag>`-then-language element structure; stray or legacy nodes before `<Tag>` can leave raw `TXT_KEY_...` text in the UI. When the receiving text collection has no XDR schema, validate well-formedness with MSXML 3 and run this cross-file key check instead of treating the absent XDR as a pass.

For every changed owning-info XML collection, scan for empty elements—not only missing elements—across the complete collection. `minOccurs`/`maxOccurs` validation permits structurally present empty tags, but a direct DLL getter can assert on them. For optional source fields omitted by Fallout, inspect the receiving constructor and reader to confirm the exact effective default, then either omit the tag only if the receiver safely handles omission or materialize the verified default in the target schema's sequence position. Also audit typed references that point forward to records declared later in the same owning collection; if the DLL resolves them during sequential registration, use a supported second pass rather than dropping valid relationships.

## XML formatting standard

Keep XML human-readable and consistent with vanilla BtS files: one element per line, indentation that mirrors the element hierarchy, and compact blank-line spacing between records. Do not serialize a collection or record into a long single line. When a mechanical edit must reserialize XML, preserve the file's XML declaration, encoding, line endings, comments, and vanilla-style indentation; review the diff for unintended whitespace churn before validation.
